# Model routing

My model choices for coordinators, children and reviewers. Apply the selection order in `agent-workflow`.

## Tiers

- Roles name tiers, not versions. At the start of a task, read the live host catalog and resolve each tier to the newest generally available model of its family. A model I pin for a session or task stays pinned and is never upgraded automatically. Never guess an ID or successor the catalog does not list.
- **Premium** (currently Claude Fable and OpenAI Astra) costs more than the workhorse. Use it only when I ask. A premium coordinator's children use the tiers below.
- **Flagship** (currently Claude Opus) takes complex work, UI and UX completion passes and final validation.
- **Workhorse** takes long-running, cost-efficient work, including whole features and UI.
- **Fast** takes short, well-defined tasks.
- Never use Haiku for code or technical work, including through helper agents. It may do non-technical work.
- Place a model in a tier by its role in the catalog, not by its name. OpenAI has one or two flagships beside all-round models such as Sol.

| Coordinator | Host | Fast | Workhorse | Complex work | Finishing and reviews |
| --- | --- | --- | --- | --- | --- |
| Claude | Multi-provider | Sonnet high | Sol high | Opus high | Opus high, plus a Sol high review |
| Claude | Claude only | Sonnet high | Opus medium | Opus high | Opus high |
| Sol | Multi-provider | Sol medium | Sol high | Sol high | Opus high, plus a Sol high review |
| Sol | OpenAI only | Sol medium | Sol high | Sol high | Sol high |

Opus is costly with tight limits, so a Claude coordinator sends long feature work to Sol when it can. Under a Sol coordinator, Sol fills every tier and Opus does only the finishing pass. Sonnet always runs at high effort. Use the coordinator I select. By default, use the highest available approved coordinator outside the premium tier.

**Do** Keep the explicitly pinned model for this task.  
**Avoid** Apply the catalog default to a pinned task.

## Splitting work

- The fast tier takes lookups, small fixes and mechanical edits.
- The workhorse takes long feature work whose design is settled, UI included, plus broad implementation and tests.
- Complex work goes to the complex-work column, never down to the workhorse: an open design question, high-risk implementation (security, privacy, budgets, data integrity), difficult debugging, or work a workhorse attempt already failed.
- Use the finishing column for the browser pass and code validation that final reviews do not cover.
- Use the finishing column for independent, high-effort final reviews of changes beyond a small fix or docs-only edit. On a multi-provider host use Opus and Sol. On a single-provider host use two from the best allowed model.
- A stronger family, or a cheaper one at the same quality, can take over a tier. Propose it with evidence, and I approve before the examples here change.

**Do** Give a settled feature to the workhorse.  
**Avoid** Give an open design choice to that tier.

## Running children

- Set the model and options through the host's supported mechanism. Use inheritance when it already gives the intended model. Check the provider, model and options each child actually ran with.
- If the policy cannot be honored, say so and continue with an allowed model. Never silently substitute another family.
- Continue available work during a rate limit. Use an allowed workhorse and record the deferred flagship pass. Retry only after the reported cooldown. If no reset time is given, do not poll or retry automatically. Use one independent workhorse review while waiting. Report any project review still unmet.
- In T3 Code, a rate-limited run resumes on its own. Do not relaunch it unless it is confirmed dead, and say so. Cancelling a task also stops its resumed runs.
- In T3 Code, reports from a child's own reviewers arrive at the coordinator. Forward them to the child that needs them.

**Do** Check the provider, model and options before relying on a child result.  
**Avoid** Silently accept a different family.
